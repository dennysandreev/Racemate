# RaceSide Plus — эксплуатационный регламент

Дата: 15 сентября 2026 года.

## Основное правило

Доступ выдаётся только после валидного webhook ЮMoney/Tribute или ручной сверки реально найденной операции администратором. Redirect пользователя после оплаты ничего не активирует. Никогда не меняйте `billing_orders.status` напрямую.

## Webhook не пришёл

1. Запустите `billing.reconcile_yoomoney`: задача вызовет Supabase Edge Function с read-only токеном ЮMoney и сверит свежие pending и истёкшие заказы по точному `label`.
2. Найдите заказ в `/admin/billing` по номеру заказа, пользователю или provider reference.
3. Проверьте состояние endpoint и последние `billing_notification_events`.
4. Сверьте сумму, валюту, способ, время и ID операции в кабинете провайдера.
5. Если автоматическая сверка не нашла операцию, используйте `Сверить оплату` только после ручного подтверждения операции, укажите реальный ID, фактически зачисленную сумму, время и причину.
6. Убедитесь, что заказ стал `paid`, появился один период, а пользователь видит зелёный статус Plus.

## Неверная сумма или валюта

- Не выдавайте доступ вручную до выяснения причины.
- Сохраните ID заказа и provider event ID; не копируйте секрет или исходное подписанное тело в тикет.
- Сверьте server-side price snapshot с кабинетом провайдера.
- Если сумма относится к другому заказу, не переносите транзакцию редактированием БД.

## Повторное уведомление

Повтор — штатная ситуация. Уникальные ограничения на provider transaction, event и order period должны оставить одну транзакцию, один период и одно исходное письмо. Проверяйте `attempts` в журнале, не создавайте новый период вручную.

## Пользователь оплатил дважды

1. Найдите оба provider transaction ID и оба внутренних заказа.
2. Если обе операции валидны, каждый оплаченный заказ создаёт отдельный последовательный период; остаток первого периода не теряется.
3. Если согласован возврат одной операции, сначала выполните его у провайдера, затем используйте `Зафиксировать возврат` с ID возврата и причиной.

## ЮMoney или Tribute недоступен

- Не отключайте entitlement enforcement: уже оплаченный локальный период продолжает работать без провайдера.
- Отключите только соответствующий checkout flag, чтобы скрыть неработающий вариант.
- Проверьте очередь pending-заказов после восстановления. Старые попытки закрывает `billing.expire_orders`.

## Внутренняя ошибка после валидного webhook

Проверенное нормализованное событие остаётся в `billing_notification_events` со статусом `failed`; исходное тело и секрет не сохраняются. `billing.retry_failed_events` повторно применяет его идемпотентно. После восстановления запустите задачу из админки и проверьте `billing.audit`.

## Возврат

Для ЮMoney возврат сначала выполняется в допустимом операционном процессе ЮMoney. Для Tribute дождитесь подтверждения провайдера или подписанного refund event. Только после фактического возврата фиксируйте его в RaceSide. Операция требует reference и причины, попадает в audit и пересчитывает доступ.

## Письма не отправляются

1. Проверьте `RESEND_API_KEY` и `BILLING_EMAIL_FROM` (или резервный `AUTH_EMAIL_FROM`).
2. Запустите `billing.process_emails`.
3. Для одного оплаченного заказа используйте `Повторить письмо`; это не создаёт новый период.
4. Не отправляйте пользователю внутренние provider labels или webhook payload.

## Ротация секретов

1. Подготовьте новый secret в менеджере секретов, не в git.
2. Согласуйте короткое окно переключения endpoint у провайдера и приложения.
3. Выполните тестовое уведомление, проверьте подпись и журнал событий.
4. Удалите старый secret только после успешной проверки нового.

## Резервное копирование и восстановление

Финансовые таблицы не очищаются фоновыми задачами. В backup должны вместе попадать `billing_orders`, `payment_transactions`, `subscriptions`, `subscription_periods`, `billing_notification_events`, `billing_email_deliveries` и `admin_audit_log`. После восстановления запустите `billing.audit` и проверьте связи заказ → транзакция → период до включения checkout.

## Безопасные данные в логах

Допустимы: внутренний order number, сокращённый provider reference, тип события и код ошибки. Запрещены: API keys, webhook secret, полный raw body, полный номер кошелька и персональные платёжные данные.
