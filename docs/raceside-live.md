# RaceSide LIVE: запуск и проверка

Реализация относится к `15_raceside_live.md` и дополнению `16_raceside_live_weekend_sessions.md`. `/live` открыт всем посетителям. Единая модель capabilities управляет практиками, квалификацией, квалификацией спринта, спринтом и гонкой. Известные фазы квалификации берутся из Race Control; время окончания части и число проходящих пилотов не выдумываются при отсутствии данных.

## Локальный запуск

В первом терминале: `pnpm dev`. Во втором: `pnpm live:replay`. Затем открыть `http://localhost:3000/live`.

Симулятор читает существующий `/api/race-replay/11334`, сохраняет порядок событий и отправляет тот же WebSocket-протокол. Он не пишет демонстрационные данные в рабочую БД и запрещён при `NODE_ENV=production`.

Для проверки другой сессии: `LIVE_DATA_SOURCE=replay LIVE_REPLAY_SESSION_TYPE=Practice LIVE_REPLAY_SESSION_NAME='Practice 2' pnpm live`. Аналогично доступны `Qualifying`, `Sprint Qualifying` и `Sprint`. `LIVE_REPLAY_OFFSET_MS` начинает показ с нужной точки, `LIVE_REPLAY_SPEED` меняет скорость. Геометрия и исходные круги остаются данными выбранного Replay; это проверка представления, а не подмена реального спортивного результата.

Для настоящего источника: `LIVE_DATA_SOURCE=openf1 pnpm live`. Нужны существующие серверные `OPENF1_USERNAME`, `OPENF1_PASSWORD`, параметры Supabase и `OPENROUTER_API_KEY`. Секреты в `.env.local` исключены из Git. Модель транскрибации — ровно `openai/gpt-transcribe`; перевод использует `AI_SUMMARY_MODEL`. Расходы заносятся в `ai_usage_logs`, используются существующие дневной и месячный лимиты.

## Развёртывание

1. Применить миграцию `supabase/migrations/20260911164606_raceside_live.sql` к целевой БД стандартным процессом проекта.
2. Настроить серверные секреты в окружении целевого сервера. Локальный `.env.local` автоматически на сервер не переносится.
3. Пересобрать и запустить сервисы `web` и `live` из `docker-compose.yml`. Rewrite WebSocket в Next.js включается при сборке; Dockerfile задаёт внутренний адрес `http://live:3002`.
4. Существующий обратный прокси перед Next.js должен пропускать WebSocket Upgrade для `/ws/live`, сохранять Host и иметь таймаут больше периода heartbeat. Порт 3002 наружу не публикуется.
5. Проверить `/api/live/health`, `/api/live/snapshot` и подключение `/ws/live` через публичный домен.

Миграция включает RLS: браузерные роли не читают и не пишут таблицы LIVE напрямую. Все внешние API и ключи остаются в серверном процессе. Docker volume `live-spool` обязателен для сохранения очереди при перезапуске контейнера; его удаление удалит ещё не доставленную в БД историю.

## Поток данных и восстановление

Один процесс LIVE поддерживает общее OAuth/MQTT-over-WebSocket соединение OpenF1. При старте и восстановлении он заполняет пропуски REST-историей, записывает сырые location/car_data в типизированные таблицы и передаёт браузерам сгруппированные обновления. Браузер интерполирует координаты; устаревшие маркеры замирают и становятся приглушёнными. Телеметрия ограничена 60 секундами, координаты — 24 отсчётами на машину, лента — 300 событиями, радио — 200 карточками.

Запись использует дисковую очередь с атомарным переименованием файлов и идемпотентными пакетами. После финиша очередь полностью записывается, затем адаптер строит существующий Replay из собственной БД. Данные связаны с отдельным `session_key`, поэтому практика и гонка не смешиваются. Для публикации Replay нужны сопоставление с этапом и карта трассы; при их отсутствии сырая история сохраняется, ошибка видна в журнале.

Team Radio загружается в память с ограничением размера и времени. Буфер очищается и при успехе, и при ошибке. В БД и дисковой очереди остаются текст, статус, время и расход; адрес записи и аудиофайл туда не записываются. Replay показывает тексты без проигрывателя MP3. Ошибка радио не прерывает тайминг и карту.

`/health` сообщает подключение источника, время последнего сообщения, число клиентов, состояние записи и WebSocket. `degraded` требует проверки источника, БД и журнала `live`. HTTP 200 этого endpoint подтверждает доступность процесса, поле `status` — состояние данных.

## Ограничения приёмки

- Production-развёртывание и production-миграция в этой работе не выполнялись.
- MP3 двух реальных радиозаписей вернули HTTP 403 от серверов F1. Поэтому реальный путь MP3 → OpenRouter → русский перевод целиком пока не подтверждён; тест обработки использует контролируемые ответы.
- Без потока действующей сессии не подтверждены фактическая задержка OpenF1, смена сессий под боевой нагрузкой и длительная непрерывная запись.
- Countdown квалификации и зона вылета доступны только при достаточных метаданных источника; реальные OpenF1-данные этой проверки не содержали конца фазы или числа проходящих пилотов.
- Более ранние события загружаются по 100 карточек; возврат к текущей ленте не перезагружает Hub.
- При восстановлении радио используются сохранённые статусы и тексты, чтобы не оплачивать завершённую обработку повторно. Записи без завершённого результата проходят общую очередь.

Команды проверки: `pnpm lint`, `pnpm typecheck`, `pnpm build`, `node --test worker/*.test.mjs worker/live/*.test.mjs`, `node --experimental-strip-types --test src/features/race-replay/lib/*.test.mjs`.

Подтверждённые остановки и конец траектории сохраняются.

## Обновление интерфейса LIVE

3D-карта получила масштабирование, поворот, наклон, перемещение, сброс камеры и слежение за выбранной машиной. Колесо меняет масштаб, перетаскивание перемещает карту, Shift или правая кнопка с перетаскиванием поворачивают её. Кнопки используют управление камерой существующего Replay.

Панели отделены промежутками и мягкими границами, текст интерфейса использует шрифт сайта, числовые значения — моноширинный. Карточка выбранного пилота получила фотографию, основные показатели и переход к подробностям. Во вкладке пилота показаны история кругов, темп последних пяти кругов без пит-стопа, лучшие сектора, идеальный круг, текущие шины и каждый пит-стоп с отдельным временем стоянки и проезда пит-лейна. История ограничена 200 кругами на пилота, отсутствующие значения не подменяются расчётными. Нижняя панель секторов увеличена. При жёлтом флаге шапка и граница центрального блока становятся жёлтыми. Подпись о приблизительных координатах и ссылки на оригинал в событиях удалены.

Для локального примера радио симулятор принимает `LIVE_REPLAY_RADIO_FILE` с JSON `{ "test": true, "driverNumber": 44, "original": "…", "ru": "…" }`. Карточка явно помечена тестовой, не записывается в БД и не выдаётся за настоящий радиообмен.

`node scripts/check-live-radio.mjs` проверяет настоящую транскрибацию через OpenRouter и последующий перевод. Скрипт использует локальные macOS `say` и Homebrew `ffmpeg`, удаляет временное аудио при любом исходе и при успехе сохраняет тексты в `/private/tmp/raceside-radio-demo.json`. Проверка 11 сентября вернула HTTP 402: OpenRouter требует минимум $0.50 на балансе для аудио. Транскрибация и перевод этим вызовом не завершены; показанный сейчас пример текста подготовлен для демонстрации оформления.

## Сходы и временное скрытие машин

Официальные `dnf`, `dns`, `dsq` из `session_result` и явные сообщения Race Control о сходе или дисквалификации убирают машину с 2D/3D-карты, оставляя пилота в тайминге. Поздние круги, пит-стопы и координаты не отменяют подтверждённый статус. `session_result` публикуется после сессии; OpenF1 не гарантирует мгновенное сообщение о каждом сходе. `STOPPED ON TRACK` и удаление времени круга сами по себе не считаются сходом.

По отдельному правилу пользователя карта скрывает машину после 180 секунд неподвижности или отсутствия координат. Статус пилота при этом не меняется. Возобновление движения или потока координат после перерыва возвращает маркер. Таймер неподвижности считается на сервере от фиксированной точки с допуском 2 единицы SVG против дрожания координат; медленное движение накапливается относительно этой точки. Обе карты используют одинаковую проверку. Симулятор сохраняет время последнего подтверждённого положения остановившейся машины и не выдаёт эвристический сход Replay за официальный DNF.

В верхнюю панель добавлен существующий знак RaceSide. Радиокарточка стала компактнее: портрет, пилот, команда и время в одной шапке, небольшой тестовый бейдж, текст с цветовой отметкой команды и раскрывающийся английский текст.

## Жёлтые флаги на 2D-карте

2D-карта получает из общего LIVE-снимка активные маршальские сектора OpenF1. Обычные границы и номера секторов не рисуются. При секторном жёлтом флаге соответствующая часть линии трассы получает жёлтую подсветку; несколько одновременных флагов показываются вместе и снимаются независимо по сообщениям `CLEAR IN TRACK SECTOR`. Глобальный зелёный флаг очищает все подсветки. Для Мадринга в карте зафиксировано 26 маршальских секторов; для остальных карт число уточняется по поступающим сообщениям Race Control, пока метаданные не добавлены в саму карту.

Проверены 28 тестов LIVE, lint, typecheck и production build. Браузер подтвердил управление 3D, выбор пилота, отсутствие ошибок JavaScript при переключении вкладок и отсутствие переполнения страницы на 375/1024/1440 px. В текущей записи с карты скрылись PER, STR и RUS по правилу трёх минут; оставшиеся 19 машин отображаются. Высота новой радиокарточки в боковой колонке — 187 px.

## Проверка Мадринга на FP1/FP2 11 сентября

`node scripts/check-madring-live.mjs` загружает реальные OpenF1-сессии 11362 и 11363. Полностью проверяются круги, пилоты, Race Control и результаты; координаты и car_data взяты с 5-й по 20-ю минуту каждой практики. Исходные ответы и записи кешируются в `/private/tmp`, отчёт — `output/live/madring-practice-report.json`. В рабочую базу тест ничего не записывает, аудио и платная транскрибация этим скриптом не вызываются.

Обработаны 1042 записи кругов, 206 сообщений Race Control и 297506 отсчётов location/car_data. Лучшие времена всех 22 пилотов совпали с session_result обеих практик. FP1 обнаружила два расхождения из-за удалённых кругов GAS и BEA: обработка удаления/восстановления по Race Control исправлена. Сопоставление использует точное время круга, поскольку номер круга в Race Control и laps в этих данных различается. В истории удалённое время зачёркнуто и не участвует в темпе или лучшем круге.

OpenF1 вернул HTTP 500 на фильтр `date>=`; тот же запрос с `date>` прошёл. В backfill используется строгая нижняя граница на 1 мс раньше начала окна, чтобы не потерять граничные отсчёты.

Карта Мадринга согласована с моделью проекта. Преобразование координат OpenF1 в модель откалибровано по полному кругу FP2 (PER, запись laps №7; RMS 6,96 м, максимум 15,37 м — это расхождение траекторий, не точность GPS). Основная линия и прогресс используют единую систему координат модели. Пит-лейн извлечён из центрального шва `Madring_Pit_Lane_Mesh` доставляемого GLB: 456 точек, длина 908,84 м, высота совпадает с дорожной поверхностью. Эти же точки используются в 2D и 3D. `scripts/calibrate-madring-live.mjs` воспроизводит геометрию; `worker/live/tracks/madring-2026.json` — согласованная карта LIVE для circuit_key 153 в сезоне 2026, приоритетная перед старой картой БД.

Локальное воспроизведение: `LIVE_DATA_SOURCE=replay LIVE_RECORDING_FILE=/private/tmp/madring-11363-recording.json LIVE_REPLAY_OFFSET_MS=300000 pnpm live`. Это 15-минутный отрезок записи; в конце поток останавливается без выдуманного финиша всей практики. События и телеметрия сохраняют порядок, будущие результаты заранее не подгружаются.

FP3: session_key 11364, 12 сентября 2026, 10:30–11:30 UTC (13:30–14:30 Москва). Для настоящего эфира остановить локальное воспроизведение и запустить `LIVE_DATA_SOURCE=openf1 pnpm live`. Воспроизведение само в прямой эфир не переключается. Production-развёртывание и миграция LIVE в этой проверке не выполнялись; задержку действующего MQTT-потока нужно проверить на FP3.

Прошли 30 тестов LIVE, lint, typecheck, production build. В браузере проверены 2D/3D Мадринга, масштабирование и слежение, таймер практики и реальные значения телеметрии. Общий поток проходит через существующий WebSocket и хранилище LIVE.


## Исправление движения и компактности LIVE

Причина ступенчатого движения: ближайшая вершина вместо проекции на сегмент (между вершинами около 30 м). Теперь сервер непрерывно проецирует координаты, отдельно определяет движение по открытому пит-лейну и применяет гистерезис между соседними дорожками. Клиент интерполирует прогресс пит-лейна без замыкания на круг; сетевые колебания времени ограничены, чтобы приход пакета не отматывал анимацию назад. LIVE обновляет положение машины и следящую камеру на каждом WebGL-кадре, вне React; React обновляет состав машин раз в 250 мс. Обычный Replay сохраняет прежний режим рендера.

Офлайн-проверка `node scripts/check-madring-motion.mjs` использует кэш записей из `scripts/check-madring-live.mjs`. На 148 500 пакетах координат FP1/FP2 доля неизменного прогресса при перемещении GPS более метра снизилась с 57,78% / 61,17% до 0,087% / 0,193%. Это проверка устранения квантования, а не гарантия качества будущего канала OpenF1. Сохранились правила скрытия через три минуты и возврата при новых координатах.

Вся строка подробного тайминга выбирает пилота, включая последний столбец; кнопка пилота сохраняет управление клавиатурой. Из компактной карточки удалены заголовок «Выбранный пилот» и дублирующая позиция. Под трассой позиция (26 px) и код пилота расположены в одну строку.

Проверки: 36 тестов LIVE, 26 тестов движения Replay / тайминга / модели Мадринга, lint, typecheck, production build. В браузере проверены клик по последнему столбцу, Enter, отсутствие старого заголовка, порядок и размер позиции под трассой, 2D и 3D. Скриншоты: `output/playwright/madring-fixed-2d.png`, `madring-fixed-3d.png`.

После проверки локальный worker переключён на `LIVE_DATA_SOURCE=openf1`, MQTT подключён, выбрана FP3 11364. Для автоматического старта локальные процессы должны оставаться запущенными. Измерение DOM-меток в браузере на записи FP2: 241 кадр за 4 секунды, около 60 FPS; движение обновлялось между серверными пакетами. Слежение и мобильная ширина 390 px проверены.

Read-only проверка записи: Supabase возвращает PGRST205 для `public.live_sessions` (таблица отсутствует в schema cache). Production-миграция LIVE по-прежнему не применена; сырая история сохраняется в локальной дисковой очереди, состояние записи degraded. Для сохранения в БД и последующей публикации Replay нужна миграция `supabase/migrations/20260911164606_raceside_live.sql`. В этой правке production-схема не изменялась.
