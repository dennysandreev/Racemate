## 2. Что именно интегрируется

Используется **API ЮMoney для сбора денег** с переводом на кошелёк RaceSide:

- форма отправляется методом `POST` на `https://yoomoney.ru/quickpay/confirm`;
- пользователь подтверждает перевод на стороне ЮMoney;
- оплатить можно банковской картой (`AC`) или из кошелька ЮMoney (`PC`), если способ доступен для подключённого кошелька;
- RaceSide связывает перевод с внутренним заказом через поле `label`;
- ЮMoney сообщает о поступлении денег подписанным HTTP-уведомлением;
- RaceSide выдаёт доступ только после успешной серверной проверки уведомления.

Технический код провайдера в RaceSide — `yoomoney`.

Альтернативный checkout работает через **Tribute Shop API**:

- RaceSide создаёт разовый order запросом `POST https://tribute.tg/api/v1/shop/orders` с серверным `Api-Key`;
- сумма передаётся в minor units, валюта первой версии — `rub`, период — `onetime`;
- пользователь переходит только по `paymentUrl`, возвращённому API Tribute;
- RaceSide передаёт непрозрачный `customerId`, но не email и не внутренний UUID пользователя;
- подтверждение принимается только через подписанный webhook с заголовком `trbt-signature`;
- доступ выдаётся после сверки provider order ID, суммы, валюты и локального pending-заказа;
- международные карты и криптовалюта показаны отдельными пользовательскими опциями, но обе создают заказ с техническим методом `tribute`; окончательный платёжный инструмент пользователь подтверждает в hosted checkout Tribute.

Технический код провайдера — `tribute`. Оба провайдера создают только разовые платежи: повторное списание без нового действия пользователя невозможно.

Это не эквайринг ЮKassa и не автоматическая рекуррентная подписка. API сбора денег инициирует отдельный перевод пользователя. Он не даёт RaceSide права автоматически списать следующий платёж с карты.

До production нужно подтвердить у ЮMoney, что тип и статус кошелька, лимиты и условия сервиса допускают коммерческий приём платежей за подписку. Публичная документация позиционирует API сбора денег прежде всего как инструмент переводов в кошелёк, поэтому юридическую пригодность нельзя выводить только из наличия технической формы.

## 3. Тарифы и продление доступа

| Код               | Пользовательское название          |  Оплата |           Срок доступа | Автосписание |
| ----------------- | ---------------------------------- | ------: | ---------------------: | ------------ |
| `plus_monthly`    | RaceSide Plus на месяц             |   249 ₽ |    1 календарный месяц | Нет          |
| `plus_first_year` | RaceSide Plus на первые 12 месяцев | 1 990 ₽ | 12 календарных месяцев | Нет          |

Оба тарифа оплачиваются одним отдельным переводом. Никаких последующих списаний без нового действия пользователя нет.

Правила периода:

- первая покупка начинается со времени подтверждения перевода;
- новая покупка при действующем доступе продлевает его от текущего `current_period_end`, поэтому оплаченные дни не теряются;
- месяц считается календарным месяцем, а не 30 днями;
- 12 месяцев считаются календарным периодом, а не 365 днями;
- после окончания срока пользователь самостоятельно оплачивает новый период;
- неуспешная новая попытка не сокращает уже оплаченный период;
- цена после первых 12 месяцев утверждается отдельно до показа следующего годового предложения;
- право на цену `plus_first_year` и возможность применить её после ранее оплаченного месяца должны быть окончательно зафиксированы до production.

Цена никогда не принимается из браузера. Сервер получает код тарифа и сам выбирает активную версию цены. Все цены первой версии хранятся в RUB.

## 4. Checkout

Checkout доступен только после входа. Изначально срок и способ оплаты не выбраны. Сначала пользователь выбирает `Год` или `Месяц`, после чего под сроками раскрываются способы оплаты. Гостя направляют на авторизацию только после обоих выборов; после входа срок и визуальный вариант оплаты восстанавливаются из безопасных параметров.

Способы в интерфейсе:

- название: `Российская карта`;
- подпись и фирменный знак: `ЮMoney`;
- действие: `Перейти к оплате`.

- `Visa и Mastercard` с логотипом Tribute;
- `USDT, TON` со знаком криптовалюты и подписью `Через Tribute`.

Две опции Tribute нужны для понятного выбора направления оплаты, но не являются техническим preselect: Shop API создаёт общий заказ без поля payment method. Доступность и окончательный выбор конкретного инструмента определяет hosted checkout Tribute.

Состояния `/plus`:

- гость видит описание и цены; `Оформить Plus` ведёт на вход с безопасным возвратом на выбранный период;

Страница получает metadata, canonical `/plus`, OpenGraph-изображение в стиле RaceSide и продуктовые analytics events: просмотр страницы, выбор периода, переход к авторизации, начало checkout и возврат. В события не передаются email, `label`, `operation_id` и платёжные данные.

После выбора Server Action:

1. проверяет сессию, origin и допустимость тарифа;
2. создаёт внутренний заказ со статусом `pending`;
3. фиксирует снимок названия, суммы, срока и условий;
4. создаёт непрозрачный `label` длиной не больше 64 символов;
5. возвращает только разрешённый action URL и серверно рассчитанные поля формы;
6. браузер отправляет обычную HTML-форму непосредственно в ЮMoney.

Поля формы:

| Поле            | Значение                                                          |
| --------------- | ----------------------------------------------------------------- |
| `receiver`      | Номер подключённого кошелька RaceSide из server-only конфигурации |
| `quickpay-form` | Фиксированное значение `button`                                   |
| `paymentType`   | `AC` для карты или `PC` для кошелька ЮMoney                       |
| `sum`           | Цена заказа строкой с двумя знаками после запятой                 |
| `label`         | Непрозрачная ссылка на внутренний заказ, не email и не user ID    |
| `successURL`    | Фиксированный HTTPS URL возврата RaceSide                         |

Пример `label`: `rs_7f3a2c1e9d8b4a65`. По нему нельзя определить пользователя, тариф или email. В БД хранится уникальное соответствие `label → order_id`.

Сумма `sum` — это сумма, списываемая у пользователя. ЮMoney удерживает комиссию из суммы, поступающей получателю. Поэтому цена заказа сверяется с `withdraw_amount`, а фактически зачисленная сумма отдельно сохраняется из `amount`.

## 5. Возврат пользователя

`successURL` нужен только для навигации. Он не доказывает оплату и не меняет заказ.

После возврата RaceSide читает локальный заказ владельца и показывает одно из состояний:

- `Проверяем оплату` — подписанное уведомление ещё не обработано;
- в состоянии обработки доступны `Повторить оплату` для повторного открытия того же заказа и `Отменить оплату` для возврата к выбору срока и способа;
- `Оплата прошла успешно` — заказ подтверждён и доступ выдан;
- `Оплата не завершена` — заказ закрыт без подтверждённого перевода;
- `Не удалось проверить оплату` — временно не удалось прочитать состояние; доступ не выдан.

API сбора денег документирует `successURL`, но не отдельный гарантированный fail callback. Если пользователь закрыл форму, он может повторно открыть тот же checkout или закрыть попытку вручную. Отмена сокращает срок текущего pending-заказа, а следующий checkout переводит его в `failed` с причиной `expired`. Позднее валидное уведомление всё равно применяется к заказу, чтобы подтверждённый перевод не потерялся.

Страница может ограниченно опрашивать локальный статус заказа. Такой polling не обращается к ЮMoney и прекращается после подтверждения или таймаута.

## 6. HTTP-уведомление ЮMoney

Endpoint первой версии:

```text
POST /api/billing/notifications/yoomoney
Content-Type: application/x-www-form-urlencoded
```

ЮMoney отправляет уведомления для переводов из кошелька (`p2p-incoming`) и с карты (`card-incoming`). Один кошелёк поддерживает один URL уведомлений, поэтому префикс `rs_` в `label` отделяет RaceSide от других возможных форм того же кошелька.

### 6.1 Проверка подписи

Для подлинности используется поле `sign`:

1. взять все полученные параметры кроме `sign`;
2. отсортировать параметры по имени от A до Z;
3. закодировать значения по UTF-8 и RFC 3986;
4. соединить пары `key=value` символом `&`;
5. вычислить HMAC-SHA256 с секретом HTTP-уведомлений;
6. представить результат в нижнем HEX;
7. сравнить с `sign` constant-time способом.

Устаревшее поле `sha1_hash` не используется для доверия. Если оно присутствует, оно остаётся обычным полем исходного уведомления и участвует в HMAC-строке по документированному правилу «все поля кроме `sign`».

### 6.2 Обязательные проверки

После валидной подписи RaceSide проверяет:

- `label` существует, имеет префикс RaceSide и соответствует одному заказу;
- заказ принадлежит провайдеру `yoomoney` и ещё не был оплачен другой транзакцией;
- `operation_id` не обрабатывался ранее;
- `notification_type` равен `card-incoming` или `p2p-incoming` и соответствует фактическому способу оплаты;
- `currency` равен `643`;
- `withdraw_amount` точно равен зафиксированной цене заказа;
- денежные значения разобраны как decimal/minor units без JavaScript floating-point сравнения;
- `unaccepted` равен `false`;
- дата и формат остальных обязательных полей корректны.

`amount` может быть меньше цены из-за комиссии. Разница между `withdraw_amount` и `amount` сохраняется для финансовой сверки, но не уменьшает оплаченный пользователем срок.

### 6.3 Идемпотентная обработка

В одной транзакции:

1. сохраняется событие с уникальным `operation_id`;
2. блокируется соответствующий заказ;
3. заказ переводится из `pending` в `paid`;
4. создаётся `payment_transaction`;
5. создаётся или продлевается оплаченный период;
6. обновляется агрегированное состояние подписки;
7. ставится в очередь одно подтверждение оплаты;
8. событие помечается обработанным.

Повтор валидного уведомления возвращает HTTP 200, но не создаёт второй период и не отправляет второе письмо. Уведомление с неверной подписью, неизвестным `label` или несовпадающей суммой не выдаёт доступ и попадает в безопасный журнал/алерт.

ЮMoney делает ограниченное число повторных доставок. В API сбора денег нет отдельного merchant status endpoint для заказа RaceSide. Поэтому пропущенный webhook нельзя «додумать» по `successURL`: он разбирается через журнал уведомлений и историю кошелька. Автоматическую сверку через Wallet API можно рассмотреть позже только с минимальными read-only правами и отдельной оценкой риска токена кошелька.

## 7. Подтверждение оплаты

Страница называется **`Подтверждение оплаты`**, заголовок успешного состояния — **`Оплата прошла успешно`**.

Она показывает:

- номер заказа RaceSide;
- тариф;
- сумму, списанную у пользователя;
- дату подтверждённого перевода;
- способ оплаты: `Банковская карта` или `Кошелёк ЮMoney`;
- оплаченный период и дату окончания доступа.

Действия: `Перейти в аккаунт` и контекстное действие `Открыть LIVE` или `Открыть телеметрию`.

Это подтверждение сервиса RaceSide, а не кассовый или фискальный чек. Оно не заменяет документ, который продавец обязан сформировать по применимому законодательству. Юридическая схема чеков и возвратов утверждается до production отдельно от названия этой страницы.

Подтверждение отправляется на подтверждённый email аккаунта, если он есть. Ссылка доступна только владельцу заказа после входа и не содержит платёжный секрет, номер кошелька или внутренний user ID.

## 8. Жизненный цикл подписки

В первой версии нет состояний автопродления и задолженности, потому что ЮMoney не списывает деньги автоматически.

| Состояние | Доступ | Значение                                                                    |
| --------- | ------ | --------------------------------------------------------------------------- |
| `active`  | Да     | Текущая дата находится внутри хотя бы одного оплаченного периода            |
| `expired` | Нет    | Все оплаченные периоды завершены                                            |
| `revoked` | Нет    | Доступ остановлен после подтверждённого возврата или решения администратора |

Источник истины — оплаченные периоды в локальной БД. Заказ `pending` не даёт доступ. Провайдерский redirect не даёт доступ. Временная недоступность сайта ЮMoney не отзывает ранее оплаченный период.

За 7 и 1 день до окончания RaceSide может отправить email `Подписка скоро закончится`, если транзакционный email подключён и пользователь не отказался от необязательных напоминаний. Telegram не используется как единственный канал напоминания, потому что после истечения подписки его доставка приостанавливается.

## 9. Модульная архитектура

Первая реализация содержит адаптеры `yoomoney` и `tribute`. Провайдер выбирается только при создании checkout; выдача entitlement остаётся provider-neutral.

```text
UI / Server Actions
        │
        ▼
Billing application service ─── Price catalog
        │
        └── PaymentProvider: yoomoney / tribute
        │
        ▼
Orders / transactions / subscriptions / periods
        │
        ├── Entitlement service ── LIVE / Telemetry / Telegram / Ads
        ├── Billing worker ─────── expire / notify / audit
        └── Admin operations ───── inspect / reconcile / refund record
```

Capability-based контракт не заставляет ЮMoney реализовывать несуществующие операции:

```ts
interface PaymentProvider {
  code: "yoomoney" | "tribute" | string;
  capabilities: {
    automaticRenewal: boolean;
    remoteStatusLookup: boolean;
    apiRefund: boolean;
  };
  createCheckout(input: CreateCheckoutInput): Promise<HostedForm>;
  verifyNotification(input: RawNotification): Promise<ProviderEvent>;
  getPaymentStatus?(providerPaymentId: string): Promise<ProviderPayment>;
  refund?(input: RefundInput): Promise<RefundResult>;
}
```

У адаптера ЮMoney все три capability-флага равны `false`. Tribute поддерживает создание hosted order и подписанные события, но RaceSide всё равно не включает автоматическое продление. Новые провайдеры добавляются без изменения модели entitlement и оплаченных периодов.

Предпочтительная структура:

```text
src/lib/billing/
  catalog.ts
  types.ts
  repository.ts
  service.ts
  access.ts
  providers/yoomoney.ts
src/app/plus/page.tsx
src/app/account/subscription/page.tsx
src/app/account/subscription/actions.ts
src/app/payment/return/page.tsx
src/app/payment/confirmation/[orderNumber]/page.tsx
src/app/api/billing/notifications/yoomoney/route.ts
src/app/api/live/access-ticket/route.ts
worker/billing/
```

Server Components читают тариф и подписку. Server Actions создают заказ и форму для действий пользователя. Route Handler принимает внешние HTTP-уведомления. Все платёжные точки работают в Node.js runtime; HMAC реализуется через `node:crypto`. Новая npm-зависимость для ЮMoney не требуется.

## 10. Модель данных

Все суммы хранятся целым числом в копейках. Внешние decimal-строки разбираются без двоичного floating point.

### `subscription_plans`

- `id`, стабильный `code`, пользовательское название;
- длительность периода и набор entitlement;
- `active`, `created_at`, `updated_at`.

### `subscription_prices`

- `id`, `plan_id`, `provider`, `currency`, `amount_minor`;
- `version`, `valid_from`, `valid_to`, `active`;
- признак first-year eligibility, если он утверждён.

Старая цена не редактируется задним числом. Заказ хранит price snapshot.

### `payment_orders`

- внутренний UUID `id` и безопасный публичный `order_number`;
- `user_id`, `plan_id`, `price_id` и price snapshot;
- `gross_amount_minor`, `currency`, `provider`;
- запрошенный `payment_method`;
- уникальный `provider_label`;
- `status`: `pending`, `paid`, `failed`, `refunded`;
- `failure_code`, `expires_at`, `paid_at`, `failed_at`, `refunded_at`;
- `created_at`, `updated_at`.

### `payment_transactions`

- `id`, `order_id`, `provider`;
- уникальный `provider_transaction_id` из `operation_id`;
- `payment_method`: `bank_card` или `yoomoney_wallet`;
- `gross_amount_minor` из `withdraw_amount`;
- `net_amount_minor` из `amount`;
- `provider_fee_minor`, `currency`, `occurred_at`, `created_at`.

### `subscriptions`

- `id`, `user_id`, `plan_id`;
- `status`, `current_period_start`, `current_period_end`;
- `last_paid_order_id`, `created_at`, `updated_at`.

В V1 у аккаунта одна агрегированная подписка RaceSide Plus. Полная история находится в периодах и заказах.

### `subscription_periods`

- `id`, `subscription_id`, nullable `order_id`;
- `starts_at`, `ends_at`, `status`;
- `source`: `payment`, `admin_grant`, `admin_adjustment` или `refund`;
- nullable `created_by_admin_id`, обязательная для admin-операции причина, idempotency key и timestamps.

Partial unique для непустого `order_id` не позволяет одному заказу создать два периода. Отдельная уникальность admin idempotency key не позволяет повторной отправке формы дважды продлить доступ. Период с `source = admin_grant` не требует заказа и не попадает в платёжную выручку.

### `billing_notification_events`

- `provider`, уникальный `provider_event_id` из `operation_id`;
- `provider_event_type`, `provider_label`;
- `signature_valid`, `status`: `received`, `processed`, `rejected`, `failed`;
- очищенные проверочные поля или hash исходного тела;
- `attempts`, `last_error`, `received_at`, `processed_at`.

### `billing_email_deliveries` и audit

Email-таблица фиксирует шаблон, заказ, адрес, статус, попытки и provider message ID. Ручные возвраты, выдачи, отзывы и сверки записываются в административный audit trail с причиной и автором.

### RLS

- пользователь читает только собственную подписку, безопасное представление заказов и подтверждения;
- anon и authenticated не вставляют и не меняют billing-таблицы напрямую;
- `provider_label`, raw notification, secret и внутренние audit-поля не выдаются клиенту;
- запись выполняют только сервер и worker через service role;
- администратор видит минимально необходимые поля без секретов и полного номера кошелька.

## 11. Проверка платного доступа

Единый серверный сервис принимает entitlement:

```ts
type Entitlement =
  | "live"
  | "telemetry_full"
  | "telemetry_demo"
  | "telegram_notifications"
  | "ads_disabled";
```

Проверка выполняется в каждой точке выдачи данных.

### LIVE

- `/live` серверно показывает рабочий терминал только подписчику;
- `/api/live/snapshot`, `/history` и radio audio проверяют доступ до proxy;
- `/ws/live` получает короткоживущий подписанный access ticket;
- live-server проверяет подпись, expiry, audience и nonce до WebSocket upgrade;
- origin check и лимит соединений остаются дополнительной защитой.

### Telemetry Hub

- гость не получает каталог и comparison payload;
- аккаунт без подписки запрашивает только server-owned demo ID;
- сервер сам выбирает разрешённую конфигурацию `N−2`;
- `compare`, `tasks`, `catalog`, `lap`, `permalink`, saved comparison и share-image используют одну policy;
- подписчик получает полный доступ;
- прямая ссылка или API-запрос не обходят paywall.

### Telegram

- создание link token, подключение и изменение настроек требуют активной подписки;
- enqueue выбирает только подписчиков;
- непосредственно перед `sendMessage` worker повторно проверяет период;
- после окончания срока account и preferences сохраняются, доставка приостанавливается;
- после новой оплаты доставка возобновляется без повторной привязки и без отправки устаревшей очереди.

### Реклама

- `ads_disabled` вычисляется сервером;
- подписчику рекламный компонент не попадает в HTML и не делает ad-запрос;
- auth, checkout, payment и account/subscription всегда без рекламы;
- LIVE не содержит рекламы;
- Telemetry Demo допускает один блок вне графиков.

## 12. Операции пользователя и администратора

Пользователь может:

- создать новый заказ;
- перейти на форму ЮMoney;
- увидеть локальный статус и подтверждение;
- продлить подписку ещё на месяц или 12 месяцев;
- просмотреть историю оплаченных периодов.

Кнопок `Отключить автопродление` и `Возобновить автопродление` нет, потому что автоматического продления нет.

Администратор может:

- найти заказ по номеру, пользователю, `label` или `operation_id`;
- увидеть причину отклонённого уведомления без секретных данных;
- сверить перевод с историей кошелька;
- повторно применить ранее проверенное событие идемпотентно;
- после фактического возврата отметить полный или частичный возврат;
- вручную выдать или отозвать период только с обязательной причиной;
- повторно отправить подтверждение оплаты.

Прямая запись статуса `paid` из админской формы запрещена. Ручная сверка использует отдельную операцию с подтверждением, ссылкой на реальный перевод и audit trail.

### Выдача RaceSide Plus в `/admin/users`

В существующем разделе пользователей добавляется колонка или компактный блок `RaceSide Plus` со статусом, датой окончания и действием:

- без активного периода: `Выдать Plus`;
- с активным периодом: `Продлить Plus`;
- после окончания: `Выдать снова`.

Форма выдачи открывается в подтверждаемом диалоге и содержит:

- пользователя: имя и email только для проверки цели, без возможности изменить их в форме;
- срок: `1 месяц`, `12 месяцев` или `Другая дата`;
- рассчитанные сервером начало и новая дата окончания;
- обязательное поле `Причина` с пояснением `Видна только администраторам`;
- действие подтверждения `Выдать Plus` или `Продлить Plus`.

Перед подтверждением интерфейс прямо сообщает результат: `Доступ будет открыт до {date}`. После успешной операции показывается `RaceSide Plus выдан до {date}`. При конфликте или повторной отправке форма перечитывает актуальный срок и не создаёт второй период.

Server Action:

1. вызывает `requireAdmin()` до создания service-role клиента;
2. валидирует target user, разрешённый вариант срока, будущую дату, причину и idempotency key;
3. в транзакции блокирует агрегированную подписку пользователя;
4. для активной подписки начинает добавленный срок после `current_period_end`, для неактивной — от текущего момента;
5. создаёт `subscription_periods` с `source = admin_grant`, без заказа и платёжной транзакции;
6. атомарно обновляет агрегированный срок, инвалидирует entitlement cache и возвращает новую дату окончания;
7. записывает `subscription.grant` в `admin_audit_log` с автором, пользователем, сроком, причиной и результатом.

Браузер не передаёт готовые `starts_at` и `ends_at` для стандартных сроков и не может напрямую записать период. Admin grant не создаёт `paid`-заказ, не отправляет подтверждение оплаты и исключается из revenue, ARPU и paid conversion.

## 13. Worker и фоновые задачи

В существующую очередь добавляются:

- `billing.expire_subscriptions` — завершить истёкшие периоды;
- `billing.expire_orders` — закрыть старые pending-заказы без подтверждённого перевода;
- `billing.send_confirmation` — один раз отправить подтверждение;
- `billing.send_expiry_reminders` — при разрешении отправить напоминание за 7 и 1 день;
- `billing.retry_failed_events` — повторить внутреннюю обработку уже проверенных событий;
- `billing.audit` — найти paid без периода, дубли `operation_id`, неверную сумму и расхождение периода.

Задачи автоматического списания и provider renewal отсутствуют.

## 14. Возвраты

API сбора денег ЮMoney не предоставляет RaceSide merchant-операцию автоматического возврата. Возврат выполняется допустимым способом в аккаунте/операционном процессе ЮMoney, после чего администратор фиксирует подтверждённый результат в RaceSide.

До production нужно утвердить:

- срок, в который пользователь может запросить возврат;
- полный и частичный возврат;
- момент прекращения доступа;
- правила возврата использованной части периода;
- обязательную ссылку на операцию возврата в audit.

Нельзя перевести заказ в `refunded` только по обращению пользователя или нажатию админской кнопки до фактического возврата денег.

## 15. Безопасность и отказоустойчивость

- Production использует только HTTPS `successURL` и notification URL.
- Секрет уведомлений существует только на сервере/worker и не имеет префикса `NEXT_PUBLIC_`.
- Сервер принимает только `application/x-www-form-urlencoded` с ограниченным размером тела.
- HMAC считается по точной документированной канонической строке; подпись сравнивается constant-time способом.
- `label`, `operation_id`, сумма и валюта имеют UNIQUE/transactional защиту от повторов.
- Сумма формируется сервером и сверяется по `withdraw_amount`.
- Checkout ограничивается по user ID и IP распределённым limiter. Текущий in-memory limiter недостаточен для нескольких процессов.
- Неизвестное или некорректное уведомление не раскрывает наличие заказа в ответе.
- Секрет, полный raw body и номер кошелька не попадают в клиент, обычные логи или Sentry.
- ЮMoney не получает доступ к Supabase и не управляет entitlement напрямую.
- Недоступность ЮMoney не закрывает уже оплаченный локальный период.
- При недоступности billing-БД платные данные не открываются всем.

## 17. Наблюдаемость

Минимальные метрики и алерты:

- созданные заказы по тарифу и способу;
- конверсия `pending → paid`;
- время от HTTP-уведомления до активного доступа;
- неверная подпись, неизвестный `label` и несовпадение суммы;
- повторные `operation_id`;
- pending старше внутреннего срока;
- paid-заказ без периода;
- email не отправлен;
- подписка скоро закончится/закончилась;
- попытки открыть LIVE, полный Telemetry или Telegram без entitlement.

Логи не содержат секрет уведомлений, email, полный номер кошелька и исходный подписанный payload.

## 20. Решения, обязательные до production

1. Подтвердить, что условия и статус кошелька ЮMoney допускают коммерческую продажу подписки.
2. Проверить лимиты кошелька, карты РФ, кошелёк `PC`, комиссии и реальные уведомления.
3. Утвердить, кто оплачивает комиссию и что финансово приемлемо получать сумму за вычетом комиссии.
4. Утвердить eligibility цены 1 990 ₽ и цену следующего годового периода.
5. Утвердить срок жизни pending-заказа и поведение позднего валидного уведомления.
6. Утвердить refund-политику и операционный способ возврата через ЮMoney.
7. Определить продавца, оферту и правила кассы/фискальных документов.
8. Выбрать сервис транзакционных email. SMTP Supabase для auth-писем сам по себе не является billing mailer.
9. Выбрать fallback-демо телеметрии до третьего завершённого этапа сезона.
10. Утвердить рекламного провайдера и consent/privacy-сценарий.
